# 03 — Key Management and Identifier Lifecycle

## Thesis

An Autonomic Identifier is not a name that points at a key; it is the head of a signed, append-only history of its own key state, and everything an adversarial reviewer needs to understand about KERI's key management follows from taking that sentence literally. The identifier is derived from its inception event, so it cannot be separated from the key material that first controlled it; authority moves forward through rotation events that are cryptographically chained to a commitment made *before* the current keys were ever exposed; and the single most important structural fact -- the one that distinguishes KERI from every certificate, token, and DID method a reviewer is likely to bring priors about -- is that control authority is split in two. Signing authority (the current keys) does the day-to-day work and is deliberately treated as expendable; rotation authority (the *next* keys, published only as a hash) is the crown jewel, held offline, and its compromise is the one unrecoverable event in the whole system. This section walks the lifecycle in the order the protocol enforces it: inception, the transferable/non-transferable fork, the establishment-versus-interaction distinction, pre-rotation and the family of rotations built on it, multisig, cooperative delegation, witness and backer designation, recovery (superseding) rotation, the as-of-anchor rule that defeats retrograde attacks, and the KERIA/Signify edge-versus-agent custody split that puts all of this into production. Throughout, it separates what the keripy/keria/signify code actually enforces from what the prose merely describes, because in a security review the gap between the two is where the defects live.

## 1. The lifecycle in one frame: the KEL and its event types

The Key Event Log (KEL) is "a Verifiable data structure that is a backward and forward chained, signed, append-only log of key events for an AID. The first entry... must be the one and only Inception event." (KERI spec, termdefs; also spec-body.md L176) "Each KEL is somewhat like a 'blockchain' that manages the key state for one and only one AID." (KERI spec, L31) It is doubly hash-chained: backward via the digest of the previous event (`p` field), and forward via the pre-rotation commitment to the next keys' digests. (KERI spec, L31, L176)

Key events come in five ilks: inception (`icp`), rotation (`rot`), interaction (`ixn`), delegated inception (`dip`), and delegated rotation (`drt`). (KERI spec, L1748) The primary papers reduce this to three families for the non-delegated case: "inception (`icp`), rotation (`rot`), interaction (`ixn`) (anchors data/seals without changing keys)." (`keri-primer.md` §2, in raw/05 L130) "The head of the log *is* the current state, and anyone can verify it offline, at any time." (`cr-ad-trust.md` §4) That last property -- offline, authority-free verifiability -- is the whole point: a verifier establishes who controls an AID "by replaying its KEL from inception, not by querying any trusted directory or CA." (`00-lens.md` claim 1)

The **key state** is what a replay computes: current public keys plus signing threshold, pre-rotated next-key digests plus next threshold, the witness list plus witness threshold, and configuration traits. It is time-dependent, established at inception, and evolves only via establishment events. (KERI spec, termdefs "Key state") In keripy this state object is `Kever` (the key-state machine) with its persisted `KeyStateRecord`; `Kever.incept` sets `verfers`, `tholder` (signing threshold), `ndigers` (next-key digests), and witnesses "from the event body itself." (`core/eventing.py:2323`; raw/09 §1)

## 2. Inception: how an AID is born

Inception is the genesis event, and its constraints are the tightest in the protocol because everything downstream depends on them.

- **Sequence number must be zero.** keripy: `if self.sner.positive: raise ValidationError(f"Nonzero sn... in inception event")` (`eventing.py:2335-2336`; KERI spec L323). There MUST be exactly one inception per AID: "There MUST be only one Establishment event that is an Inception event. All subsequent Establishment events MUST be Rotation events." (KERI spec, L1378) A second sn=0 with a different SAID is treated as likely-duplicitous (escrow and raise). (`30-invariants.md` B1; `31-landmines.md` L8)
- **The identifier is the digest of the inception event.** For a self-addressing (transferable) AID, the `d` (SAID) field and the `i` (identifier) field "MUST have the same value and same derivation code," and validation requires `d == i`. (KERI spec, L1380-1381) keripy computes the SAID by the dummy-fill method: copy the event, fill the `d` field with the non-Base64 dummy char `#` sized to the digest, serialize, digest, and overwrite the field with the result (`coring.py:4058-4096`, `Saider._derive`; `serdering.py:Serder.makify`; `30-invariants.md` B5). "Changing field order/serialization changes the SAID." (`30-invariants.md` B5) This is the primer's "crystallized fact": the identifier is a tamper-evident commitment to the exact bytes of the event that created it. (`keri-primer.md` §3.2)
- **The signing threshold size cannot exceed the number of keys:** `if len(self.verfers) < self.tholder.size` -> "Invalid sith" (`eventing.py:2340`).
- **Configuration traits are fixed at inception and constrain the whole KEL.** The Establishment-Only (`EO`) trait forbids interaction events, so every event must be signed by first-time one-time pre-rotated keys and signing-key reuse becomes impossible; a validator MUST drop non-establishment events for such an AID. (KERI spec, L377) The Do-Not-Delegate (`DND`) trait means a validator MUST drop delegated events whose delegator carries it. (KERI spec, L379)

The derivation is the fork in the road. The **basic** derivation embeds the public key directly in the prefix (CESR code `B` = "Ed25519 verification key non-transferable"; `1AAA`/`1AAC`/`1AAI` for non-transferable ECDSA/Ed448/secp256r1). The **self-addressing** derivation uses a digest of the inception event (code `E` = Blake3-256). (`coring.py:244-294`; raw/09 §1) "The code prefix (the leading selector char) tells the verifier the crypto suite -- crypto agility is structural, not negotiated." (raw/09 §1) Only prefixive codes may be AIDs: `Prefixer.__init__` raises `InvalidCodeError` if the code is not in `PreDex` (`coring.py:3830-3831`).

## 3. Transferable versus non-transferable AIDs

This is a fork with sharp, load-bearing consequences, and it is a place where a reviewer's instinct is frequently wrong.

A **non-transferable** AID cannot rotate. "A basic SCID... does not support Rotation... and therefore MUST be abandoned once the controlling private key becomes weakened or compromised." (KERI spec, L107) The papers put it plainly: basic AIDs are "suitable only for ephemeral, short-lived use cases." (`keri-primer.md` §2.1; raw/05 L98) The identifier *is* the key digest, so changing the key means abandoning the identifier and all reputation attached to it.

A **transferable** AID survives rotation precisely because it is derived from the entire inception event -- initial keys plus the pre-rotation commitment -- rather than from a bare key. "The identifier string remains constant even as the keys change... Identity survives key rotation." (`keri-primer.md` §2.1; raw/06 §1.1) This is the tetrad: for transferable AIDs a fourth element, the KEL, joins the triad of identifier/keypairs/controllers to "persist bindings across rotation," and "The essence of the KERI protocol is a strongly bound tetrad." (KERI spec, L162-182)

**The correction to the outsider prior.** Non-transferability is *not* expressed by a special prefix code as a general matter; it is expressed by an empty next-key commitment. "Non-transferability in KERI is expressed by an empty next-key commitment (`ncount=0`, `nsith='0'`), not by a special prefix code -- except where a basic non-transferable code like `Ed25519N` legitimately carries the key itself." (`31-landmines.md` L1) keripy enforces the empty-commitment side of this hard: a non-transferable prefix MUST have empty next digests, empty witness list, and empty anchored data at inception -- `if not self.prefixer.transferable and ndigs:` -> ValidationError "Invalid inception next digest list not empty for non-transferable prefix" (`eventing.py:2352-2355`, `:2362`, `:2383`; `30-invariants.md` C4). Rotation is forbidden when there is no prior next commitment: `if not self.ndigers: raise ValidationError("Attempted rotation for nontransferable prefix...")` (`eventing.py:2650-2653`). Rotating to a null next-key list on a transferable AID is itself the abandonment signal: "no more key events MUST be allowed in its KEL." (KERI spec, L340, L174)

**The landmine here is real.** keripy's `Hab.incept` (and `GroupHab.incept`) hardcodes `code = MtrDex.Ed25519N` for *any* non-transferable AID regardless of the actual signing-key type (`habbing.py:2931`, `:3728`). This is correct for Ed25519 but wrong for a future Falcon non-transferable AID, which needs a digest-based prefix. (`31-landmines.md` L1) A reviewer of post-quantum work should treat this as a known defect, not a template.

**Witnesses must be non-transferable.** When a backer AID serves as a witness it "MUST be non-transferable, fully qualified public keys" so a validator can verify a witness receipt straight from the AID with no witness KEL needed. (KERI spec, L353, L1252) The security analysis is emphatic that this is a *specification* constraint, not a discretionary simplification: treating it as optional is "a characterization error about KERI-as-specified." (`background.md` §2.3; raw/07 §6)

## 4. Establishment versus interaction events

The establishment/non-establishment split is the axis on which authority turns.

- **Establishment events** (`icp`, `rot`, `dip`, `drt`) establish or change key state. **Non-establishment events** (`ixn`) anchor data via seals but change no key state. (KERI spec, L1751-1752)
- **Establishment events gate authority.** Current keys always come from the last establishment event; a message (including an `ixn`) is authorized only if its signatures satisfy that establishment event's current `Tholder` threshold. (`30-invariants.md` B4; `background.md` §3.4)
- **Interaction events cannot change keys and cannot supersede anything** (see recovery rotation below). Their job is to bind external data to key state at a point in the sequence via seals, which is what gives an anchored signature its permanence. Sealing is "an indirect signature that persists across key-state change... validity persists in spite of later changes to the key state... essential for unbounded term but verifiable issuances." (KERI spec, L1280, L395)

Why the distinction matters for security: exposing a signing key repeatedly (as interaction events do) widens the window in which a stolen current key can be used, but it never risks rotation authority, which the next-key commitment already protects. An AID that wants to eliminate even the signing-reuse window declares the `EO` trait and signs *every* event with fresh one-time pre-rotated keys. (KERI spec, L377) A seal's ordering is itself meaningful -- "ordering of seals = verifiable ordering of endorsements." (KERI spec, L395)

## 5. Pre-rotation: the firewall and the crown jewel

Pre-rotation is the mechanism that makes a transferable identifier survivable, and its full security philosophy is developed in Section 02 (survivability, the detection-and-rotation race, the catastrophic-versus-survivable asymmetry). Here the concern is the mechanics -- exactly what is committed, exactly what is checked, and exactly where the reference code can go wrong.

**What is committed.** Every establishment event names the *current* signing keys in cleartext (the `k` list) but the *next* keys only as digests (the `n` list). "control authority is split between keypairs that hold signing authority and keypairs that hold rotation authority." (KERI spec, §Pre-rotation, L1364) The knowledge base compresses the doctrine to a slogan: "Pre-rotation is the firewall; the next key is the crown jewel." (`00-lens.md` claim 4) The next key itself "stays offline, in cold storage" (`cr-ad-trust.md` §4); the primer's operational rule is that "The next (rotation) key must be managed differently/independently from the current key -- offline, air-gapped, cold storage, different device. This independence is what makes pre-rotation a real firewall." (raw/05 L95; `keri-primer.md` §2.3)

**Why it is post-quantum by construction.** The commitment is a hash of a public key, and hashes resist quantum attack far better than signatures: Grover's algorithm gives only a quadratic speedup, not Shor's exponential one, so a 256-bit hash "retains roughly 128 bits of post-quantum security." (`cr-ad-trust.md` §3-§4) A quantum adversary who breaks the current signing key "gains the ability to forge interaction events -- but not to rotate, because the pre-rotation commitment is protected by a hash." (`cr-ad-trust.md` §4) The kspqs royal-succession analogy is the clearest statement of the timing: "commitment precedes exposure... The quantum-vulnerable public rotation key is only revealed at the exact moment it is used, after which authority has already passed to a new, secret successor. The attacker is always one step behind." (raw/05 L62-63) The pre-rotated keys "serve as first-time, one-time, and only-time rotation keys in the next rotation operation." (KERI spec, L1628)

**Exactly what is checked at rotation.** keripy's `Kever.exposeds` is the firewall in code (`eventing.py:2940-2984`). For each rotation signature it takes the prior next-key digest at the signature's `ondex`, recomputes `Diger(ser=siger.verfer.qb64b, code=diger.code).qb64` over the newly revealed public key, and requires it to equal the committed digest (`eventing.py:2980-2982`). Only signatures whose revealed key hashes to a committed digest are counted. Then the exposed keys must satisfy the *prior* next threshold: `if not self.ntholder.satisfy(indices=ondices):` -> escrow plus `MissingSignatureError` "Failure satisfying prior nsith" (`eventing.py:2853-2863`). A rotation is therefore valid only if the newly revealed keys both hash to the previously committed digests *and* satisfy the prior next threshold -- "An attacker holding only current signing keys cannot rotate -- they do not know the pre-images." (raw/09 §2) The dual index is the enabling mechanism: keripy's `Siger` carries both `.index` (into current keys) and `.ondex` (into prior-next digests) (`eventing.py:2942-2984`). Rotation events therefore need up to two indices per signature -- "Second index looks up prior-next digest, first index the exposed key, verify digest, then verify signature." (KERI spec, L1256) A subtle cross-implementation rule: `ondex` must be computed from the *prior* establishment event, not the proposed one (signify-ts issue #378). (raw/10 §6d)

**The implementation defect a reviewer must guard.** The `exposeds` check can go *permissive* on a digest-code mismatch. Because the revealed key is re-digested using the *committed* digest's code, a wrong or mismatched code causes the recomputed digest not to match, and the `ondex` is "silently excluded from threshold satisfaction rather than failing closed -- weakening the pre-rotation check (the firewall, C1)." (`31-landmines.md` L6, flagged HIGH) New digest codes (Falcon/PQ) widen this surface. The standing invariant is "Never weaken or short-circuit this." (`30-invariants.md` C1) A companion defect sits one layer up: `Serder._compute` overwrites the SAID field from raw bytes and "a wrong digest code yields an invalid SAID with no error." (`31-landmines.md` L7, HIGH)

## 6. Rotation and the general pre-rotation family

A basic rotation reveals the previously committed next keys as the new current keys, signs with them, and commits to a fresh next set. But the spec defines a whole family of rotations, and a reviewer should know they exist because they encode governance patterns that simpler systems cannot express.

- **Partial rotation** holds some pre-committed next keys in reserve rather than promoting all of them; **augmented rotation** adds new keys that were not pre-committed. In both cases "A rotation's current key list MUST be satisfiable w.r.t. BOTH prior-next and current thresholds." (KERI spec, §General Pre-rotation, L1470-1498) keripy enforces both thresholds jointly (the `exposeds`/`ntholder` check above plus the current `tholder` check).
- **Reserve rotation** lets reserve keypairs contribute to availability and fault tolerance without participating unless a non-reserve member is unavailable -- the basis for "provisional/custodial/escrow control authority." (KERI spec, §Reserve Rotation, L1501-1543)
- **Custodial rotation** is the sharpest governance primitive: a custodian holds signing authority (the current keys) while the owner holds *exclusive* rotation authority (the next keys), with the exposed rotation keys given weight 0 in the new current threshold. This lets the owner "revoke custodian's signing authority unilaterally." (KERI spec, §Custodial Rotation, L1545-1576) This exact pattern is what KERIA's passcode recovery uses (Section 12).
- **Abandonment** is a rotation to an empty next list, after which no further events are allowed. (KERI spec, L340, L174)

**The post-quantum recovery variants.** SQAR (Surprise Quantum Attack Recovery) is a partial-plus-augmented rotation to post-quantum-safe signing keys; it assumes the current signing keys and the prior-next keys are not PQ-safe but the prior-next *digests* are, and it gives the rotation keys weight 0 in the new current signing threshold (rotation authority only). (KERI spec, §SQAR, L1578-1606) The hybrid-multisig hedge is complementary: a threshold requiring both an ECC signature and a PQC signature means "Even if the ECC key is broken, the attacker cannot satisfy the full threshold without also breaking the post-quantum key." (`keri-primer.md` §2.5; raw/05 L89) Crypto agility makes this a per-identifier event, not an infrastructure project: "The upgrade is an event in the KEL. Not a global infrastructure project." (`cr-ad-trust.md` §6)

**The keystore hazard.** keripy advances and erases key material *before* the rotation event is validated: `mgr.rotate()`/`replay(advance=True)` mutate `PreSit` (old -> new -> nxt) and erase old private keys before `Kever.processEvent` validates the event. "On rejection you need an explicit `replay(advance=False)` recovery; a naive caller can strand the keystore ahead of the KEL." (`31-landmines.md` L11; `30-invariants.md` G2) This is an operational, not a protocol, hazard, but it is exactly the kind of thing that bites custodial deployments.

## 7. Multisig: exposing governance, not inventing it

KERI's multisig is fractionally weighted thresholds declared in the public KEL. The `k` list holds the public keys; the threshold (`kt` for current, `nt` for next) may be a simple M-of-N hex integer or a list of rational-fraction clauses. (KERI spec, L327) Clauses are ANDed; a clause is satisfied when its verified-signature weights sum to at least 1; rational fractions (not floats) avoid rounding errors. (KERI spec, L1419) `[1/2,1/2,1/2]` means "2 of 3." (KERI spec, L1421) Nested weighted lists model multi-device contributors. (KERI spec, L1466)

The corporate-board worked example makes the expressiveness concrete: three founders and four investors, policy "majority of Founders OR supermajority of Investors," encodes as `kt = [["1/2","1/2","1/2"],["1/3","1/3","1/3","1/3"]]` -- the two subarrays are clauses joined by OR, so any two founders (0.5x2=1.0) or any three investors satisfy it. (`keri-primer.md` §2.4; raw/05 L138, L149) Break-glass recovery encodes as Phone(0.5)+Laptop(0.5)+ColdStorage(1.0) at threshold 1.0: lose the phone and the cold-storage key rotates unilaterally. "The recovery logic is baked into the math of the identifier itself." (raw/05 L150)

The doctrinal point is that KERI's contribution here "is less about inventing and more about exposing." (`keri-primer.md` §2.4) Multisig is optional but declaring and following the policy is required: "multisig is optional and infinitely variable, but defining and following policy about it is required." (`keri-primer.md` §2.4; raw/05 L99) The papers ground this in millennia of practice -- Hammurabi's law 7, Deuteronomy 19:15, double-entry accounting -- and ask why anyone imagines "it's safe to use the single-signature mechanism of X509 certs as the only gate on unlocking the entire reputation of modern corporations." (`x509-prob.md` §One key isn't realistic; raw/06 §3)

In keripy, a multisig controller is `GroupHab`; the "local" member signs at the edge and contributes indexed signatures. A landmine: the indexed-signature code silently switches encoding at index >= 63 (`Ed25519_Crt_Sig` vs `Ed25519_Big_Crt_Sig`), so "A group/rotation with >63 keys changes the Siger encoding; consumers that don't handle the 'big' indexed codes may reject." (`31-landmines.md` L14) The "Joint issuance" work extends multisig toward "a weighted threshold of endorsements, each owner signing from their own identifier, asynchronously and with no shared key" -- "lighter and composable." (`sda.md` §8; raw/06 §6)

## 8. Delegation: cooperative, two-event, two-way peg

Delegation in KERI is cooperative, and the cooperation is what gives it its distinctive security property. A delegation is *two* events that reference each other: a delegating event in the delegator's KEL that contains a seal of the delegated event, and a delegated event (`dip` or `drt`) in the delegatee's KEL that contains the delegator's AID in its `di` field. "Both MUST participate." (KERI spec, §Cooperative Delegation, L1610-1612) The delegatee's AID is the digest of its `dip` event, which itself references the delegator's AID, so the delegatee is cryptographically bound to its delegator. (KERI spec, L1616) The papers call this contain-by-construction: a delegate's "very identifier commits to its delegator," so forbidden acts are "not merely against the rules but outside the space of possible moves." (`sda.md` §7; raw/06 §6)

**The joint-compromise property.** The delegator retains establishment control authority; the delegatee gets "revokable signing authority." (KERI spec, L1618) The security consequence is that compromising the delegatee alone is not enough: "any exploiter that merely compromises only the delegate's authoritative keys may not capture the control authority... A successful exploiter must also compromise the delegator's authoritative keys." Conversely, compromising only the delegator's signing keys cannot force a delegated rotation without the delegatee's pre-rotated keys. "Both sets of keys must be compromised simultaneously." (KERI spec, L1622) This is why delegated events carry an *extra* layer against dead and live attacks: an attacker who compromises the delegatee's pre-rotated keys still needs the delegator's anchoring seal, so it "must either induce the delegator to issue a seal or must also compromise the delegator's signing keys." (KERI spec, L1688-1690)

**Config traits.** `DID` (Delegate-Is-Delegator) treats the delegatee as equivalent to the delegator for horizontal signing scale; `DND` (Do-Not-Delegate) forbids delegation. Delegation seals carried in interaction events are less secure than those in rotation events, because `ixn` is less secure than `rot`. (KERI spec, L379-381)

**What keripy actually enforces.** A delegated event is authorized only by a seal in the *delegator's* KEL; validation locates the anchoring event via the seal-source couple `(delseqner = sn, delsaider = SAID)` in `Kever.validateDelegation`. (`30-invariants.md` D1) The delegating event must be first-seen in the delegator's KEL before the delegated event is accepted, checked against `db.fons`. (`30-invariants.md` D2) The firewall rule is stated in the docstring: "The delegator MUST NOT accept a delegable event unless it is locally sourced, fully signed by its controller, and fully witnessed by its controller's designated witness pool." (`eventing.py:3087-3089`) And the delegator's approval logic is bound to witness changes: it "SHOULD NOT automatically approve a delegable rotation event unless that event's change to the witness pool is below the witness pool's prior threshold" (KERI spec, L1778) -- because a compromised delegatee could otherwise rotate in its own witnesses to bypass local security; the mitigation is a delegator time window so the delegate can *detect* the compromised superseding rotation. (`eventing.py:3099-3104`, `:3225-3238`)

**The gaps.** Three delegation landmines are live in keripy: `validateDelegation` "trusts `db.fons` even if the delegating event is only escrowed," which can falsely validate a delegate (`31-landmines.md` L13); delegated inception "has no confirmation loop; assumes delegator KEL already present," so a late-arriving delegator anchor can strand the dual-seal out of order (`31-landmines.md` L12); and a validator must be independently OOBI'd with the delegator before it can validate a delegate's KEL, because "A witness is NOT a watcher" -- witnesses store and serve but do not vouch for cross-AID anchors. (`30-invariants.md` D3; `31-landmines.md` L4)

## 9. Witness and backer designation

Witnesses are the availability and accountability layer, and a reviewer's single most common error is to read them as consensus nodes.

**What a witness is.** A witness is an entity "DESIGNATED (trusted) by the controller" that verifies, signs receipts for, and keeps events; it is the controller of its own non-transferable AID and is "Under ultimate control of the AID's controller," who may change the witness pool at will. (KERI spec, termdefs; L43) "A witness makes no such assertion. A witness simply stores and serves events." (`keri-primer.md` §2.6) The trust model toward witnesses is adversarial: "witnesses are assumed to be potentially malicious." (`keri-primer.md` §2.6)

**TOAD is not consensus.** The witness threshold is the Threshold Of Accountable Duplicity. In keripy the object is literally named for it: "`toader (Number): instance of TOAD (threshold of accountable duplicity)`" (`eventing.py:1945`). The name is the doctrine: "The witness threshold is literally named for duplicity accountability, not for consensus/finality. Witnesses provide accountability, not global ordering." (raw/09 §2) The controller declares the tally M in inception config, and "the controller accepts accountability for an event when any subset M of the N witnesses confirms that event." (KERI spec, L1846, L1850) KAWA (KERI's Algorithm for Witness Agreement) is a single-phase agreement that gives fault tolerance "without the multi-phase commit overhead of classical Byzantine Fault Tolerant algorithms like PBFT." (`cr-ad-trust.md` §4) Critically, its consistency guarantee is *local to the witness set*, not global across validators, and it does not bind a malicious controller who "can simply run its own witnesses." (`background.md` §5.8; raw/07 §2.4)

**Backers.** A backer is the ledger-backed alternative to a witness -- commonly a DLT-based registrar that anchors key events (or their SAIDs) on a ledger, requiring the `RB` config trait and a Registrar Backer Seal. (KERI spec, termdefs; L345, L494) A registry may even have zero backers: keripy's NoBackers (`NB`) trait raises `ValueError` if any backers are specified (`vdr/eventing.py:89-90`), directly contradicting the "witness = blockchain validator" prior.

**Local versus remote: the firewall as second factor.** keripy processes every event as local (protected) or remote (unprotected). "A local event may assume that the event only came via a protected transmission path... A remote event is received in an unprotected manner." (`eventing.py:3043-3047`) The purpose is "to allow increased security on local events where a threshold structure is imposed" (`eventing.py:3048-3049`): each witness only accepts local events, making "the controller's signature(s) the first factor and the set of unique witness factors a secondary threshold factor." An attacker must therefore compromise "not merely the controller's private key(s) but also the unique second factor on each of a threshold satisfycing number of witnesses." (`eventing.py:3051-3057`) The code even strips remotely sourced signatures from locally-membered indices before counting the threshold, "So that attacker can't source remotely compromised but locally membered signatures to satisfy threshold." (`eventing.py:2780-2791`)

**Witness invariants and one defect.** TOAD bounds: a non-empty witness list requires `1 <= toad <= len(wits)`; an empty list requires `toad == 0`. (`30-invariants.md` F1; `eventing.py:2869-2896`) Witness-set changes have their own rules: no duplicates, cuts must be a subset of current witnesses, and cuts and adds must be disjoint; removes are processed before adds; ordered-set math preserves witness index stability for indexed receipts. (`eventing.py:2696-2726`, `:2661-2665`; KERI spec L358, L362) The spec rule for sufficiency is "receipts meeting TOAD, not all witnesses" (`30-invariants.md` F2) -- but keripy's `WitnessReceiptor` "currently waits for ALL witnesses instead," a defect (not the invariant) that blocks indefinitely if a single witness is down and is the "Likely root of open twins #855 and #912." (`31-landmines.md` L9)

## 10. Recovery (superseding) rotation

Recovery rotation is the one narrow exception to first-seen dominance, and understanding it is understanding how KERI reconciles "first seen, always seen, never unseen" (KERI spec, L49) with the need to recover from compromise.

The base invariants are that at most one valid KEL exists per AID or none at all (KERI spec, L178), and that first-seen events are permanent. But if a current signing key is compromised, the controller needs to sign a *conflicting* event at an already-seen sequence number to reclaim control. Superseding recovery permits this under tight rules. keripy's own docstring: "Supersede means that after an event has already been accepted as first seen into a KEL that a different event with the same sequence number is accepted that supersedes the pre-existing event... This enables the recovery of events signed by compromised keys." (`eventing.py:3139-3142`)

**The forked KEL is preserved, not erased.** "the KEL is forked at the sn of the superseding event. All events in the superseded branch of the fork still exist but, by virtue of being superseded, are disputed." (`eventing.py:3143-3145`) The superseding fork is the authoritative branch; the superseded events "still remain in the KEL and may be viewed in order of their original acceptance." (`eventing.py:3148-3150`) This is duplicity-evidence by construction. The first-seen ordinal `fn` is distinct from `sn`: "Each event accepted into a KEL has a unique fn but multiple events due to recovery forks may share the same sn." (`eventing.py:3153-3155`)

**The superseding rules.** (KERI spec, L1804-1825; `eventing.py:3158-3207`)
- **A0:** a rotation may supersede an interaction at the same `sn` (provided that interaction is not before another rotation).
- **A1:** a non-delegated rotation may NOT supersede another rotation at the same `sn`.
- **A2:** an interaction may never supersede any event.
- **B:** a delegated rotation may supersede the latest-seen delegated rotation at the same `sn` under conditions governed by the delegator's KEL ordering (B1/B2/B3).
- **C:** recurse up the delegation chain to the non-delegated root; if neither A nor B is satisfied there, discard the superseding rotation.

So recovery from a compromised *current* key works (a `rot` supersedes the fraudulent `ixn`), but there is a constraint: "recovery can not happen for any compromise of pre-rotated keys, only the latest-seen." (KERI spec, L1825) An attacker who performs a compromised delegated rotation and then a following approved rotation can make recovery impossible. This is the operational face of the catastrophic-versus-survivable asymmetry: current-key compromise is survivable, pre-rotation-key compromise is not.

**Recovery is not an escape from accountability.** "Because events are signed nonrepudiably, any key compromise is still the responsibility of the controller... still may be held accountable for any harm." Recovery repairs the KEL only for *future* validators; those who already first-saw the compromised events still saw them. (KERI spec, L1792) If validators cannot universally find the same undisputed path (the "trunk"), the KEL is irreconcilable and is not trusted. (KERI spec, L1788-1790)

## 11. Key state as-of-anchor: the retrograde-attack defense

This is the deepest threat-model contribution in the corpus, and it is the property that most cleanly corrects an outsider prior. The prior is: to check a signature, check it against the signer's *current* key state. KERI says that is a "pyrrhic victory" -- "After-the-fact audits are impossible, because anything in the past can be faked with compromised keys." (`was.md` §Mitigation 3; raw/06 §2.4)

The **retrograde attack**: an attacker who *ever* obtains a key K can forge evidence "that looks like it originated in the past, forever," and this remains possible "even if she rotates or revokes K before Malfoy steals it." (`was.md` §Retrograde attack) The backdating window "has no end point." Most DIDs are vulnerable because they "can only be resolved to the current key state" (`was.md` §Mitigation 3), and SD-JWT/OAuth tokens inherit the same limitation because they "sign a key, not an identifier." (`sdjwt-acdc.md` §2.3; raw/06 §4.3)

KERI's defense is **anchored signatures validated against key state as of the anchor's sequence position**. "An anchored signature/credential is validated against the issuer key state AS OF its KEL anchor's sequence position, not current key state or wall-clock." (`30-invariants.md` H1) This is what "identity is sameness across time, a key is not" cashes out to operationally. (`00-lens.md` claim 7) keripy enforces it in `vdr/eventing.py:Tever.verifyAnchor`: `db.kels.getLast(pre, on=seqner.sn)` then `assert eserder.said == saider.qb64` -- "the anchor must be the issuer KEL event at exactly that sn." (`30-invariants.md` H1; `10-map.md`) The payoff is time-independent verification: "An analysis of an anchored signature will produce the same result no matter when it happens." (`was.md` §Conclusion) An anchored signature is not the same as a paired signature (a `proof` block bundled "because the format says so"); it is a provable association through the KEL, "independent of any container context." (`keri-primer.md` §3.3)

**The gap a reviewer must flag.** The keripy credential `Verifier` may not re-run the anchor check. `Verifier.processCredential` verifies TEL registry existence, credential iss/rev state, schema, and chain edges, "but recon found no call to `Tever.verifyAnchor` here -- anchor validation appears to happen only in `Tevery` when a TEL event is received, not when a credential + proof is verified." A credential presented with a forged `(seqner, saider)` proof "could pass schema + TEL-state checks without the anchor being confirmed against the issuer's actual KEL at that sn -- undermining invariant H1." (`31-landmines.md` L15, flagged HIGH, confidence medium) This is the single highest-value item in this section to confirm against current HEAD before relying on the credential path. The related monotonicity discipline for data at rest is BADA (Best-Available-Data-Acceptance), which guarantees monotonic ordering of signed updates to protect against replay; KEL-anchored updates accept only if the new anchor is later in the KEL than the prior's. (KERI spec, L2858, L2887-2895)

## 12. The KERIA/Signify edge-versus-agent custody split

Everything above assumes a controller that holds its own keys. In production, the dominant deployment pattern separates *who holds the keys* from *who runs the infrastructure*, and it does so without ever giving the infrastructure the keys. This is the Signify/KERIA architecture, and it is a direct instantiation of pre-rotation, delegation, and custodial rotation.

**The custody rule.** "This architecture protects the host and the holder private keys. All client tasks/calls are signed 'at the edge', not in the hosted KERIA instance." (`keria/README.md`) Of the five functions of a KERI agent -- key generation, encrypted key storage, event generation, event signing, event validation -- signify-ts "splits off two, key generation and event signing... to provide 'signing at the edge'." (`signify-ts/README.md`) The cloud agent keeps only encrypted material it cannot decrypt: "a remote cloud agent that never has access to the decryption keys," with "only the public keys and blake3 hash of the next keys made available to the agent." (`signify-ts/README.md`) This corrects the custodial-wallet/KMS prior directly: the agent "holds only encrypted key material it cannot decrypt and never signs on the controller's behalf. The custodian is a blind store + relay, not a signer." (raw/10 §4)

**The two-AID delegation spine.** The architecture is a pair of AIDs in a cooperative delegation. The **Client AID** ("caid") is the controller's own transferable AID, single signing key and single rotation key, derived at the edge from a 21-character passcode; it is the *delegator*. The **Agent AID** is a KERIA-created *delegated* (`dip`) AID whose `di` is the Client AID; it is the *delegatee*, and it signs all responses back to the client so the client can authenticate its own agent. (`protocol.md` Steps One-Three; raw/10 §1) Mutual authentication is thus "asymmetric-by-role but symmetric-in-mechanism: client signs every request with the Client AID; agent signs every response with the Agent AID." (raw/10 §1) There are no bearer tokens or API keys; identity is the AID and proof is a fresh RFC-httpbis message signature per request over `@method`, `@path`, `signify-resource`, and `signify-timestamp`. (raw/10 §4)

**What the code enforces at the boundary.** signify-ts verifies the delegation binding on connect: the Agent's inception must be `dip` (`if (state['et'] !== Ilks.dip) throw ... 'invalid inception event type'`), must carry a delegator anchor (`if (!state['di']) throw new Error('no anchor to controller AID')`), and must have exactly one signing key, one next key, and threshold exactly 1 for both (`controller.ts:44-82`). KERIA refuses to make a multisig group an agent controller: "multisig groups not supported as agent controller" (`agenting.py:871`). Every admin request and response must be signed, or KERIA short-circuits with HTTP 401 (`authing.py:187-189`); the client rejects a response from the wrong agent ("message from a different remote agent," `clienting.ts:243`) and a missing delegation anchor ("commitment to controller AID missing in agent inception event," `clienting.ts:167-169`).

**Passcode rotation IS a KEL rotation -- and a custodial one.** Changing a passcode is not re-keying a vault; it is a partial rotation of the Client AID that binds old rotation authority to new signing authority. "To provide post-quantum secure passcode recovery, a passcode recovery must be accompanied by partial rotation of the Client AID." (`protocol.md` §Partial Client AID Rotation) Mechanically, the old rotation key `R0` (regenerated from the old passcode) and a new signing key `S0` (from the new passcode) co-sign: `S0` gets fractional weight 1 (full authority), `R0` gets weight 0 (no authority but proves possession), and a dual-indexed signature satisfies the prior next-key commitment. (raw/10 §2) This is exactly the custodial-rotation pattern from Section 6 -- weight-0 rotation keys proving possession while transferring signing authority -- applied to passcode recovery. KERIA detects an interrupted rotation and "lock[s] out all other operations until it is completed successfully," using the old encrypted passcode as the recovery breadcrumb, deleted only on success. (`protocol.md` §Passcode Rotation Recovery)

**Edge key-derivation methods.** The keys themselves are derived by one of several documented methods, all sharing the property that unencrypted private material never leaves the edge: **Salty** (one random salt per AID, Argon2-stretched over a path from prefix and key indices, salt stored server-side X25519-encrypted as `sxlt`); **Randy** (fully random keys, each stored as an encrypted CESR `Cipher` blob); **Sandy** (a different salt per inception and rotation); **Group** (manages no keys at all -- designates the local participant in a distributed multisig); and experimental **HSM** integration. (`protocol.md` §Key Generate Methods; raw/10 §5) On rotation the edge re-derives and validates each managed AID's keys against its published key state before re-encrypting: the Salty path throws "Invalid Salty AID" if the derived public keys do not match the published ones (`controller.ts:372-374`). A live recovery-breaking landmine sits in the Salty path derivation: `path = f"{stem}{ridx:x}{kidx+i:x}"` has no delimiter, so "when `stem` ends in a hex digit, distinct `(stem,ridx,kidx)` tuples can map to the same path -> same derived seed." (`31-landmines.md` L10; keria/signify #928)

**Cross-implementation parity is the deepest risk.** keripy, KERIA, signify-ts, and SignifyPy must agree byte-for-byte on CESR primitive encoding, key stretching (identical Argon2 salt/tier/path -> identical keypair), Serder/SAID computation, and the HTTP message-signature bytes. (raw/10 §7) The CHANGELOG parity fixes prove these are live constraints: `rotate` defaulting to the *next* threshold not the current (#208), correct `adds`/`cuts` (#359), hex-string sequence-number parsing, and the `rotated=true` flag added "to match keripy `BaseHab.sign` behaviour" (0.4.0). (raw/10 §7d) "A change that passes keripy's own tests but diverges from the spec/wire format is a defect, because it silently breaks interop." (`00-lens.md` claim 5)

## 13. What is enforced versus what is prose: the ground-truth summary

For a reviewer, the value of the reference implementation is that it draws a hard line between guarantees the code makes and guarantees the prose merely asserts. The established, machine-enforced core of the lifecycle:

- Inception sn=0, exactly one inception, `d == i` for self-addressing AIDs, threshold size bounded by key count. (`eventing.py:2335`, `:2340`; KERI spec L1378-1381)
- Non-transferable AIDs have empty next/witness/data at inception; rotation requires a prior next commitment. (`eventing.py:2352-2355`, `:2650-2653`)
- The pre-rotation firewall check: revealed keys must hash to the committed next digests and satisfy the prior next threshold. (`eventing.py:2940-2984`, `:2853-2863`)
- Backward hash chaining (`p` must match prior SAID), strictly increasing sequence numbers, current keys from the last establishment event. (`30-invariants.md` B2-B4)
- Cooperative delegation authorized only by a seal in the delegator's KEL, first-seen before acceptance. (`30-invariants.md` D1-D2)
- Superseding recovery forks and preserves the KEL rather than deleting; A0/A1/A2/B/C rules. (`eventing.py:3137-3207`)
- Local-versus-remote firewall with witness signatures as a second factor. (`eventing.py:3040-3135`, `:2780-2791`)
- Edge custody: agent never holds decryptable keys; every admin message signed; agent AID is a single-key delegated AID anchored to the client. (raw/10 §3)

The load-bearing *uncertainties and known defects* a reviewer should carry forward, none of which are protocol flaws but all of which are places a real deployment can be weaker than the doctrine promises:

- **L15 (HIGH, confidence medium):** the credential `Verifier` may not re-validate the anchor against the issuer's KEL, undermining the as-of-anchor defense (H1) for presented credentials. Confirm against current HEAD.
- **L6/L7 (HIGH):** the pre-rotation and SAID checks can fail *open* on a digest-code mismatch rather than fail closed, widening the firewall's attack surface for new (Falcon/PQ) digest codes.
- **L9:** receipting waits for all witnesses instead of TOAD, breaking availability under single-witness downtime.
- **L11/L12/L13:** the keystore advances before validation; delegated inception has no confirmation loop; `validateDelegation` trusts escrowed `db.fons` entries.
- **L1:** non-transferable AID prefix code is hardcoded to `Ed25519N`, blocking non-Ed25519 non-transferable AIDs.
- **L10:** the Signify Salty key path lacks a delimiter, risking seed collisions and recovery breaks.

The meta-rule the knowledge base states about all of this is the right note to end on: "do not 'simplify away' a guard you don't fully understand; treat an unexplained check as protecting an invariant until proven otherwise." (`00-lens.md` claim 6) In the lifecycle above, nearly every "redundant-looking" check -- the dual index, the local/remote split, the two-way delegation peg, the weight-0 rotation key -- is encoding a security guarantee that a simpler design cannot offer and cannot retrofit.
