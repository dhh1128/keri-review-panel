# DESIGN — one runner for every engine

This file records why the panel runs through an engine-neutral runner (`cli/`) that replaced the original Claude Workflow, what was decided, what was rejected and reversed, and what has not been verified. It is for whoever next decides whether to change the runner. The README says how to use the panel; this says why it is shaped the way it is.

## The problem

Until 2026-10-14 the panel ran only inside Claude Code. Everything that makes it good is engine-neutral markdown: `keri-doctrine.md`, `review-house-style.md`, `orchestrating-reviews.md`, `personas/*.md` and the vendored `reference/bible/`. But the thing that ran it, `keri-review-panel.workflow.js`, was a script for Claude Code's Workflow runtime: `agent()` with schema validation, `parallel()`, per-call effort and model, and a preflight that finds its own prompts through the `~/.claude/workflows` symlink. A colleague using Codex could read every persona and still had no way to run the panel. Daniel asked whether it could move to Codex, Cursor or Copilot, and wanted a Codex session to argue the design with.

The design below came out of that argument. Codex's full contributions are in two rounds in `.ignored/portability/codex-reply.md` (not tracked); the decisions that came from it are restated here so they survive that file.

## Decisions

**One runner, many backends.** `cli/keri-review-panel.mjs` owns all orchestration as code — fan-out, concurrency, the dedupe_key merge, the verify gate, persistence — and makes each agent call through a backend adapter (`cli/lib/backends.mjs`). Two backends exist: `codex` (`codex exec --output-schema`) and `claude` (`claude -p --json-schema`). An engine can be chosen per run, per persona, or for the verify step, so a finding can be refuted by a different lab's model than the one that raised it. The reason this is worth more than portability: correlated blind spots between reviewer and refuter are the panel's main residual weakness, and a second lab is the cheapest decorrelation available.

**Node, so the Workflow's logic moved over nearly verbatim.** The Workflow was already JavaScript. Python was considered and gained nothing but a translation step in which parity bugs could hide.

**Personas return their report as data; the runner writes every file.** Each review call returns `{report_markdown, findings}` as one structured result. In the Workflow the agent wrote its report file and separately returned a manifest, and nothing checked that the two agreed. Returning both together removes that divergence and lets reviewers run read-only (`--sandbox read-only` for Codex, read-only tools for Claude), which in turn means a headless run never stalls on an approval prompt. This was Codex's proposal. `orchestrating-reviews.md` §7 now says so for unattended mode; an interactive reviewer, with a human present, still writes its own file.

**The proposal is fetched deterministically and snapshotted before any model sees it.** GitHub PRs, issues and discussions go through `gh`; other URLs through `curl`; files are read; text is taken as given. The raw snapshot is written to `<out>/proposal/` with its source, retrieval time, sha256 and (for a PR) the head commit, and it is passed to every agent fenced as untrusted data. Codex's point, and a good one: GitHub content is mutable, so two runs are only comparable if each records exactly what it read. A deterministic fetch does not make the LLM normalization deterministic — that step is still a model call — but it makes it auditable.

**Schemas are canonicalized per backend.** Codex's structured-output mode requires every property to be listed in `required` and `additionalProperties: false`; optional fields must be expressed as nullable. The runner keeps one schema per call and derives the strict form mechanically (`canonicalize()` in `cli/lib/schemas.mjs`). Every result is re-validated by the runner after parsing, whatever the backend claims, plus semantic checks the schema cannot express: id prefix matches the persona, ids are unique, dedupe_key is kebab-case, the report is non-empty. One retry with the validation errors appended; then the persona is recorded as failed rather than silently dropped.

**Effort names map per engine.** Personas declare `medium` or `deep`. `deep` is not a setting either engine knows: it maps to `high` for both.

**The pipeline follows the contract where the Workflow did not.** `orchestrating-reviews.md` §9 says merge by exact key, then semantic dedupe, then verify. The Workflow verified raw findings before either merge. The runner follows §9, so verify runs once per surviving issue rather than once per duplicate. Likewise, the Workflow's default output directory was `<date>-<milestone>` and a same-day rerun overwrote it; the runner suffixes `-2`, `-3`. The verify gate is otherwise kept exactly: CRITICAL, any SEC finding regardless of severity, or an invulnerability objective (`all` mode: CRITICAL/HIGH recommending revise or reject).

**Progress is visible without the Workflow UI.** Losing `/workflows` was the main cost Codex named. The runner writes one timestamped line per event to stderr and to `<out>/progress.log`, records every call (engine, model, effort, duration, cost when reported, exit status) in `<out>/run.json`, and keeps each persona's raw result under `<out>/raw/`, so a failed run can be inspected and its completed reviews are not lost.

**One SKILL.md front end for every host.** Codex and Copilot CLI discover skills at `.agents/skills/<name>/SKILL.md` (user-level `~/.agents/skills/`) and Claude Code at `~/.claude/skills/<name>/SKILL.md`, all with `name` and `description` frontmatter. `install.sh` links `skill/` into each. The skill tells the host agent to run the CLI in the background, watch `progress.log`, and read the synthesis — it does not orchestrate anything itself.

**The Claude Workflow is retired; this runner is the only one.** This reverses the original plan, which kept the Workflow as the reference implementation until a fixed set of proposals had shown parity. One parity pair was run (see Known gaps), it agreed on everything that drives a decision, and on 2026-10-14 Daniel collapsed to one runner rather than wait for more pairs. The reasoning: two orchestrators of one contract drift, and a follow-up to retire one later is the kind that gets forgotten, so keeping both bought parity evidence at the price of a standing drift risk with no owner. What was given up: parity rests on one pair, so a systematic difference between the runners (the CLI rated matched findings about one severity step lower) cannot yet be told from variance; and Claude Code users lose the `/workflows` progress view, replaced by `progress.log`. The Workflow is recoverable from history at `6ad3e2c:keri-review-panel.workflow.js`, and a second parity pair can still be run against that copy if the severity question matters.

## Rejected alternatives

**Port by rewriting the orchestration as prose in a per-engine SKILL.md, and let each engine's own subagents do the fan-out.** Rejected by Claude in the first proposal and confirmed by Codex from the documentation: Codex subagents support parallelism and per-agent model/effort, but no per-child output schema, they inherit the parent's sandbox and approval mode, and a new approval request fails in an unattended flow. Prose orchestration also makes the merge and the verify gate non-repeatable, and produces one divergent copy per engine.

**Extract pure JS helpers shared by the Workflow and the CLI.** Codex's first migration plan. Rejected in round two because a Workflow script is self-contained — it cannot `import` or `require` — so "shared" helpers would be copy-pasted, which is the drift the plan was meant to avoid. Codex agreed, adding the caveat that became the parity condition, later reversed (above): `claude -p` is a fresh process per call and is not automatically equivalent to Workflow `agent()`.

**A four-backend runner up front.** Codex's strongest pushback: Cursor and Copilot adapters would be written with no evidence those CLIs offer equivalent tool access, schema enforcement or sandboxing. Accepted. Only `codex` and `claude` are built; others wait for a probe.

**`claude --bare` for headless Claude calls,** to skip the user's hooks and CLAUDE.md. Rejected because bare mode reads auth only from `ANTHROPIC_API_KEY`, so it fails on a subscription login. The backend instead passes `--settings '{"disableAllHooks":true}'`, `--strict-mcp-config` and `--no-session-persistence`, so a review call does not register itself with session-coord or the tmux registry.

## Review history

The first cut of `cli/` was reviewed adversarially by Codex (gpt-6-sol, read-only) in three rounds: ten findings on the first cut, all fixed before the first commit; a re-review that found four fixes partial and six new defects; and a third pass that found four small remaining gaps (a blocker hidden by a higher-severity accept, a heading regex matching across a newline, a bare heading passing, an unsorted list after verify). All were fixed, with a test for each in `cli/test/`. The third round ended with prompt injection as the one accepted residual. The ones that changed the design, so a later reader does not undo them:

- **Claude reviewers get `--tools Read,Grep,Glob`, not just `--allowedTools`.** `--allowedTools` only pre-approves; it neither removes other tools nor overrides a user setting that allows `Edit`. The first cut also allowed `Bash(git log:*)`, and `git log --output=<file>` writes, which matters because the proposal is untrusted input. (Raised independently by Codex and by the security-guidance plugin.)
- **A merged item is a group of whole claims, each gated and verified on its own** (`cli/lib/merge.mjs`, tested in `cli/test/merge.test.mjs`). This took two rounds. The first cut raised only the severity on merge, which could produce `HIGH / recommend-accept` and escape both the blocker count and `--verify all`. The second kept the most severe claim whole and verified the group as one, and Codex's second review showed that still failed three ways: a severity tie hid a reject behind an accept; a group confirmed by its weak claim still published the refuted strong claim's severity; and the verify gate read only the representative's objective, so a merged invulnerability claim was never checked. What holds now, after a third round caught a CRITICAL/recommend-accept outranking a HIGH/recommend-reject: the representative is the strongest *surviving* claim — any blocking claim first, then severity, most blocking disposition, confidence — and a refuted claim leaves its group without lending it anything. The general mistake, for the next merge you write: once two claims share an item, any field read from "the item" is a choice of whose claim to believe, and that choice must be made after verification, not before.
- **Overlapping semantic-dedupe groups are skipped, not chained,** so `[A,B]` and `[B,C]` cannot collapse two issues that need different changes.
- **Fences carry a per-run random token,** so proposal text cannot close its own fence and speak as the runner.
- **The report must give each finding its own section headed by its exact id** (`### SEC-F1: …`), checked by the runner with an anchored match; a substring check let `SEC-F10` stand in for `SEC-F1`. This enforces that every manifest finding is explained, not that the explanation is good.
- **`bucket` is required and must be one of the contract values**, per `orchestrating-reviews.md` §8. The Workflow's schema left it optional. Since 2026-10-15 there are four, `defect`, `deployment-gap`, `proof-scope` and `non-goal`, matching the doctrine's evidence standard; before, a defect in the specification or the code had no value of its own.
- **`--milestone` is restricted to a filename-safe slug,** since it becomes part of paths.
- **Accepted residual risk: prompt injection is mitigated, not prevented.** Proposal text and reviewer output are fenced with a per-run token and labelled as data, but the boundary is still a convention inside one user prompt, which a model can be talked out of. What limits the damage is that every agent is read-only and the runner validates every result; a successful injection can distort findings but cannot write files or run commands.
- **Output directories are reserved with a non-recursive `mkdir`,** and an existing `--out` is refused, so concurrent runs cannot share one; `run.json` is rewritten after every call, so a killed run keeps its audit; a failed summary makes the run `degraded` (exit 3) rather than silently complete.

## Known gaps

- Cursor and Copilot backends do not exist, so those agents can host the skill but the reviewers still run on codex or claude. On 2026-10-14 both `codex exec` and `copilot skill list` discovered the skill from `~/.agents/skills`; neither has yet been watched invoking it end to end from a conversation. Cursor's support for `SKILL.md` is unverified.
- **Parity with the retired Workflow rests on one pair (2026-10-14), which agrees at the level that matters, not item for item.** WebOfTrust/keripy discussion #1515 (SEDI unary edge operators) went through the Workflow and through the CLI on `--engine claude`, default four personas, keripy @0f1966f88, concurrency 2 each. Both took about 13 minutes; the CLI reported $11.49 in 13 calls, with no retries or errors. Both reached the same verdict (not sound as written), the same CRITICAL (keripy silently drops unknown unary operators at `verifying.py:435`, so `[E1E, DI1I, NI2I]` leaves the issuer unchecked; raised by all four personas in both runs), and the same headline fix (unary operators must be must-understand). Roughly half the remaining items correspond — optional authority edge, inherited authority not re-checked for revocation, undefined conflict class, DI2I unimplemented, no present user for most of the family — usually with the CLI one severity step lower. Each run also found things the other did not: only the CLI found that the default operator is decided from the far node's disclosure form (HIGH, verified); only the Workflow found the vdr/IPEX evaluator divergence and I2I/I1I token confusability. With one pair, none of these differences can be told apart from run-to-run variance, so this is evidence that the runners are the same instrument, not a measurement of it. Outputs: `.ignored/keri-review-2026-10-14-parity-{wf,cli}/` (not tracked).
- **The parity pair exposed a gate asymmetry in the runner, which the Workflow shared.** The CLI's verifier refuted SEC's "optional authority edge" claim, while GOV's version of the same issue was not grouped with it by semantic dedupe and, not being a SEC claim, was never verified, so it stands as a HIGH blocker beside its own refutation. The Workflow's gate had the same property; it did not show there only because that run's dedupe grouped the claims. The default gate verifies by who raised a claim, not by what it claims. Not changed: `--verify all` closes it at the cost of more calls, and whether that should be the default is a judgement about cost, not a bug.
- Evidence beyond that is three smoke runs on 2026-10-14, all on one 360-character toy proposal (an ACDC `expires` field) against keripy: SEC+SKP on codex alone, the same on claude alone, and SEC+SPC+SKP on codex with verify and summary on claude. All completed with schema-valid results and no retries, and their findings were on-topic and grounded in keripy. That proves the plumbing, not the panel's quality on a real proposal, and none of it is a parity comparison against the Workflow.
- The proposal fetcher handles GitHub PRs, issues and discussions. Other hosts get a raw `curl`, which for an HTML page is noisy and may be wrong; there is no readability extraction.
- Running Codex from inside another sandboxed Codex session fails at startup (its app-server cannot write its state). The CLI must be launched from a normal shell, or the host agent must request escalation for it.
