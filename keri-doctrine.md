# KERI Doctrine — a house-style file for adversarial review

## Reading stance

This document exists to make an AI reviewer reason in KERI's own terms. It is not a neutral summary and not advocacy. Its job is to stop the reviewer from importing priors from PKI/X.509, IAM/OAuth/OIDC/SAML, blockchain/consensus, and mainstream verifiable-credentials work (W3C-VC, SD-JWT, DID methods) that KERI contributors have deliberately and specifically rejected. A critique built on a smuggled prior is not merely wrong; it is unfalsifiable from inside the outsider's model, because the reviewer keeps finding "missing" features that were never meant to exist.

Use this file the way a house-style guide is used: as the register and vocabulary you write in, not as a source you cite. When you need to ground a finding, cite the primary sources (spec sections, the Hardman papers, `background.md`, the keripy knowledge base) that this file points to, not this file.

Three disciplines govern the register:

- **Hedged, non-advocacy.** State KERI's claims as KERI states them, then state the boundary. KERI's own corpus is candid that some outsider critiques survive reframing (immature observer tooling, thin formal literature, no eIDAS-equivalent legal standing). A reviewer who cannot separate a category error from a genuine residual will either dismiss KERI wholesale or swallow it wholesale, and both are the same failure of discipline (`dg-c02-claude.md` §5-6; `wtbo.md` §5-6).

- **Guarantees are conditional.** Every KERI security property must be stated relative to its assumptions. "Agreement thresholds do not imply global safety... Failure to state these boundaries results in overstated guarantees" (`background.md` §4.7, §5.10). The assumption catalog A1-A13 (`background.md` §4.6) names the axes along which a real deployment can silently fall short. Treat each named assumption as a place to press, never as free.

- **Objective function first.** KERI is survivability-oriented, not invulnerability-oriented. Before you evaluate any claim, name which objective function the criticism assumes. The analysis method requires restating a claim verbatim before assessing it: "you MUST restate the claim verbatim... If you cannot do so, stop and ask" (`standard-analysis.md` §0). A reviewer who cannot say which objective function a criticism assumes has not yet earned the right to make it.

**Citation durability, refreshed 2026-09-15.** Citations now rest on these commits: keripy `b8f60166b`, KERI spec `main` `fbdd4a615` and `v1.1` `3753f3797`, CESR spec `main` `bad6edd84` and `v1.1` `65fd7518b`, ACDC spec `main` `f0bd097de` and `v1.1` `2362e48a1`, Dossier spec `b9227753c`, papers `181569b64`, keri-security-analysis `149fa6c35`, keripy-knowledge `9489ac9bd`, KERIA `7e685edaa`, signify-ts `ffba8406e`. Treat the **quoted text and `§section` anchors as the citation of record**; any bare line number (`L1234`, `file.py:NN`) is a *hint* valid only as of those commits and WILL drift. Re-anchor before relying on a line number: run `refresh/freshness.py`, which greps each quoted span against the live sources and reports it as live or missing. Personas re-anchor at review time against whatever source they are pointed at; they never cite a line they have not just re-confirmed.

## The load-bearing claims

These are the doctrinal commitments a KERI reviewer must share. Each is stated crisply with a citation.

1. **The root of trust is the identifier's own key-event history — there is no authority.** An AID is self-certifying: cryptographically derived from its own controlling keys, so its authenticity is proven by replaying its Key Event Log (KEL), not asserted by any CA, registry, ledger, or federation. "This root-of-trust is cryptographic, i.e. not administrative, because it does not rely on any trusted third-party administrative process but is established with cryptographically verifiable data structures alone" (KERI spec §End-verifiable, L89). "The head of the log is the current state, and anyone can verify it offline, at any time" (`cr-ad-trust.md` §4). Asking "who is the CA / who vouches for the identifier" presumes an administrative layer the design deletes.

2. **Survivability, not invulnerability.** KERI's objective function is mission survivability — continue functioning under attack, make hostile acts observable and attributable, preserve evidence for recovery — not the prevention of entire attack classes. "KERI is explicitly not designed around invulnerability. Its security posture is more accurately understood through the lens of mission survivability" (`background.md` §4.5.1). Forks and equivocation by a malicious controller are "anticipated disturbances, not protocol failures." Criticizing KERI for not preventing malicious-controller duplicity "is analogous to criticizing a smoke detector for not preventing fires" (`dg-c02-claude.md` §5).

3. **Detection, not prevention; duplicity-evident, not duplicity-resistant.** KERI does not try to make equivocation impossible — that would require global consensus. It makes duplicity "provable and attributable" via nonrepudiable cryptographic proof (`wtbo.md` §4; `cr-ad-trust.md` §4). Unlike Certificate Transparency, KERI detects duplicity in key state "via nonrepudiable cryptographic proofs of Duplicity, not merely the detection of inconsistency... that MAY or MAY NOT be duplicitous" (KERI spec, L85). One valid copy of a KERL is enough to convict any inconsistent copy — "the existence of an alternate but Verifiable KEL for an identifier is provable evidence of Duplicity," and "there MUST be at most one valid KEL for any identifier or none at all" (KERI spec, L178) — and a detected fork is "fatal to the reputation of the identifier" (`keri-primer.md` §2.6). But nonrepudiability is not detection. The proof is conclusive only once two conflicting copies are placed side by side, and KERI guarantees no such meeting: detection is observer-dependent (assumptions A8-A11, none enforced), and duplicity "may persist indefinitely without detection" (`background.md` §6.7). Claim the strength of the evidence, never the certainty of catching the act. "Any claim that implies prevention must be scrutinized for hidden assumptions" (`background.md` §4.5).

4. **Zero-trust verifier, possibly-malicious controller.** Verifiers assume nothing about controller honesty; "Protection against a fully malicious controller" is an explicit non-goal (`background.md` §1.3, §2.1). Every externally supplied event, signature, key, receipt, or credential is "hostile input until verified... 'looks well-formed' is not 'is authorized'" (keripy `00-lens.md` claim 3). The honest-controller premise that appears in the strongest formal proofs is "a proof-technique simplification, NOT a KERI deployment requirement"; removing it "shifts the focus from prevention to detection and recovery" (`dg-c06-claude.md` §3).

5. **Validity is local and observer-dependent, not global consensus.** KERI does not promise validators will ever agree. "KERI does not guarantee global convergence"; "Permanent divergence is an allowed outcome" (`background.md` §7.4.2, §7.4.4) — and it is a protocol-level property, "permitted even with observers present" (`dg-c03-claude.md` §3). Safety means "Validators do not accept invalid histories"; it does not mean they agree on a single history (`background.md` §7.5.1). Key events are idempotent authorization operations, so per-identifier local ordering suffices where a ledger would demand global ordering: "the controller is the sole source of truth for the creation of any and all key events, it alone, is sufficient to order its own key events" (KERI spec §KAWA insight, L1836). Global total ordering across identifiers is an explicit non-goal (`background.md` §1.3).

6. **Microledgers, not a ledger — KAWA detects forks after the fact; it does not gate inclusion.** The decentralized-identity mainstream still carries blockchain intuitions: one global ledger, global consensus deciding whether and in what order an event is recorded. KERI splits "the one big blockchain in the sky" into per-identifier microledgers — each AID has its own KEL, rooted in that identifier and replicated by its own witnesses and wallets. "KERI rejects the need for global consensus regarding identity. Instead, it uses microledgers called key event logs (KELs)... The ordering of events matters only relative to that specific identifier" (`keri-primer.md`). The consequence is the point reviewers most often miss: by the time KAWA runs, the controller has *already recorded* the event on its own microledger. KAWA does not ask "should this be recorded?" — it asks the post-hoc question "is any actor trying to fork this history after the fact?" That is detection of equivocation, not consensus on inclusion. It works because key events are "idempotent authorization operations... local ordering may be sufficient for idempotency," and "because the controller is the sole source of truth for the creation of any and all key events, it alone, is sufficient to order its own key events" (KERI spec §KAWA insight, L1836). A reviewer who asks "where is the chain / why no consensus layer?" has imported the strong property (global total order) into a system that deliberately requires only the weak one (per-identifier order).

7. **Pre-rotation is a firewall between signing authority and rotation authority.** Every establishment event names the current signing keys in cleartext but the next keys only as a hash. Control authority is split "between keypairs that hold signing authority and keypairs that hold rotation authority" (KERI spec §Pre-rotation, L1364). "An attacker who steals the current key can sign events, but cannot rotate to take permanent control: they don't know the next key's value, only its hash" (`cr-ad-trust.md` §4). This makes the asymmetry a design property: compromise of current keys is survivable; compromise of both current and pre-rotated keys is "catastrophic and unrecoverable" and the identifier must be abandoned (`00-lens.md` claim 4; `wtbo.md` §5). It is also post-quantum by construction: the next keys are committed only as digests, and "a quantum computer is not advantaged over a conventional computer in inverting cryptographic strength digests" (KERI spec §SQAR, L1580) — a hash resists Grover (quadratic) far better than a signature resists Shor (exponential). Surprise Quantum Attack Recovery (SQAR) is the matching recovery path when current signing keys are not yet PQ-safe (KERI spec §SQAR, L1580). **Cite `wtbo.md` §4, not `kspqs.md`, for the strength of this guarantee**: read alone `kspqs` states it unconditionally, where `wtbo` carries the qualifier that the hash "protects the *next* key, never the one currently exposed." Two boundaries attach and neither weakens the primitive. CESR `v1.1` now concedes the same thing in specification language — hiding pre-rotated keys "protects the next key pair but does not protect the currently exposed one", and pre-rotation and post-quantum signatures are "complementary, not alternatives" (§Post-Quantum Cryptographic Primitives, `[N1.1]` @`65fd7518b`) — the first place the spec family admits pre-rotation is not a complete post-quantum answer. And the "effective 128 bits" figure is **contested by ENISA**, which argues a 256-bit output's quantum security "could arguably drop below 128 bits" and recommends 384-bit hashes; Hardman cites ENISA himself and answers with an agility argument rather than a defence of the number, so repeat it as his assessment. The counterweight belongs in the same breath: ENISA's same guidance treats hash-based mechanisms as standalone-safe while requiring lattice PQC to be hybridised, which independently supports the primitive.

8. **Signatures are validated against key state as of their KEL anchor — and that key state is the one established by the last establishment event at or before the anchor, not the state at the signer's latest event.** The second clause is not pedantry: interleaved interaction events do not move key state, and **two implementations conflated the two in the same month, six days apart, from opposite ends of the wire** (keripy `kraming.py` receiver-side 2026-09-01, KERIA `aiding.py` sender-side 2026-09-07, different authors, both from failures). Under the wrong reading, every AID that had anchored anything — so every credential issuer — had correctly formed signatures refused. The rule appears in **no specification**; it is `[K]`-only, in a keripy docstring and in code. Note also that this claim and KRAM's currency rule answer different questions in shared vocabulary: this one is about historical key state at a position, for evidence at rest; KRAM's is about which *current* key state a live message's `tsg` must name. A bare signature is "difficult to sequence relative to a compromise or revocation event"; an attacker who ever obtains a key can forge evidence that "looks like it originated in the past, forever" (`was.md`, unheaded opening, L18–33 @`181569b64` — there is no `§Retrograde attack` heading and there never has been). NIST SP 800-102 concurs: a signed message "provides no assurance that the private key was used to sign the message at that time" (`keri-primer.md` §3.3). KERI's answer is anchored signatures: an anchored signature or credential is validated against "the issuer key state AS OF its KEL anchor's sequence position, not current key state or wall-clock" (keripy invariant H1, `30-invariants.md`). ACDCs are therefore not directly signed; they are bound to the issuer's key state, which is signed — so issuer key rotation does not force mass revocation (ACDC spec §Binding to Key State, L1673-1675).

9. **The spec/wire format is the top interop invariant — passing keripy's own tests is not sufficient.** keripy is a reference implementation whose "intent layer" is exogenous: the CESR/KERI/ACDC specifications. "A change that passes keripy's own tests but diverges from the spec/wire format is a defect, because it silently breaks interop" (`00-lens.md` claim 5). CESR code-table entries and sizing, field names and order, SAID derivation, version strings, and count codes are external contracts binding keripy, KERIA, signify-ts, and SignifyPy byte-for-byte. Because CESR is self-framing (read code, look up length, read bytes), a wrong sizing entry does not throw — it silently mis-frames every downstream primitive.

10. **Complexity is load-bearing; do not simplify away a guard you do not understand.** Nearly every redundant-looking check — the dual signature index, the local/remote firewall, the two-way delegation peg, the weight-0 rotation key, the double-modulo pad formula — encodes a security guarantee a simpler design cannot offer. "Do not 'simplify away' a guard you don't fully understand; treat an unexplained check as protecting an invariant until proven otherwise" (`00-lens.md` claim 6). KERI's "oft-cited operational complexity is itself load-bearing" (`wtbo.md` §6).

11. **Correlation-resistance and data loyalty are LAYERED (ACDC-and-above) properties, not KERI-core promises.** KERI-core promises key-state continuity and duplicity-evidence; it does not promise unlinkability and cannot. Even at the ACDC layer "the primary design goal is not data privacy protection per se but the more general goal of protection from the unpermissioned exploitation of data" (ACDC spec §Disclosure Mechanisms, L1659), and cryptographic unlinkability is "a weak form... it does not prevent statistical correlation from contextual information" (§Bulk-issued, L2785). Correlation-resistance is assembled from three strata: technical disclosure (graduated/selective disclosure, blinding UUIDs), governance/contractual duty (chain-link confidentiality, data-loyalty rules in the `r` section), and deployment discipline (per-facet AIDs, unlogged one-time presentations). A critique that faults KERI-core for "not preventing correlation" is attacking the wrong layer.

12. **Cryptography reaches authenticity, not veracity — a human keeps the final trust judgment.** Authenticity ("truthfulness of an imputed origin") and veracity ("truthfulness of claimed facts in content") are "primarily orthogonal." "Judgments about authenticity can — if managed very carefully — be reduced to an objective mathematical computation, whereas judgments about veracity inherently require subjective assessments of reputation" (`authenticity-vs-veracity.md`). Verification splits into Layer 1 (cryptographic: signatures, SAIDs, KEL consistency, anchor position — universal, observer-independent) and Layer 2 (semantic: what a credential means, whether an issuer is fit — governance/human). "Automate the introduction. Automate the proof where you can. But never automate the verification of the proof" (`oia.md`).

13. **Crypto agility is designed in — a new algorithm is an event, not an infrastructure project.** A CESR derivation/type code names the crypto suite; a new suite claims a previously-unused code point. Old parsers frame streams around codes they do not know, and new parsers accept old streams: "New implementations with the new codes can accept streams from old implementations, but old ones will break if they receive the new ones" (CESR spec §Protocol genus/version codes, L618). Adding a code is a detectable minor version bump, not a silent misread. This is the post-quantum migration story: "The upgrade is an event in the KEL. Not a global infrastructure project" (`cr-ad-trust.md` §6) — unilateral, per-identifier, versus PKI's mandatory global re-rooting. The load-bearing caveat: this holds only because sizing is a pure function of the code and the new code occupies a genuinely unused slot; getting the code-table entry and sizing math exactly right is "the highest-risk surface in the flagship" (`00-lens.md` claim 8 — note that file is a **draft, unendorsed, and 493 commits stale**). Two 2026-09-15 refinements. The "sizing is a pure function of the code" caveat now has **affirmative evidence from outside keripy**: an independent implementation absorbed 33 unfamiliar post-quantum primitives with **no parser change at all**, because the table carries the sizes. And on CESR `v1.1` a new suite may **not** simply claim any unused slot — post-quantum codes MUST occupy the four-character `1`/`2`/`3` tables and MUST NOT consume the scarce one- and two-character entries, and *which* of the three is arithmetic rather than choice, fixed by raw size mod 3 (`[N1.1]` @`65fd7518b`). Allocation is now administered, and a selector encodes lead-byte alignment, not algorithm semantics. **Do not claim CESR carries normative post-quantum codes**: `main` @`bad6edd84` has zero, and no shipped implementation carries the `v1.1` table — the only implementation anywhere is an unmerged personal fork branch, which is not `[K]`.

14. **Detectability obligations are asymmetric by role — Issuer-side is mandatory, Issuee-side is elective.** The same detect-and-recover posture produces different requirements at different ends of a credential, and the reason is blast radius rather than principle. Issuer key compromise is rampant and high-ROI — "the worst form of fraud with the most widespread potential of harm… This could annihilate trust in the ecosystem" — so anchoring is compulsory and an impersonator "MUST anchor the ACDC in a TEL that is anchored in the Issuer's KEL," which is what lets an Issuer detect fraud "without requiring the cooperation of any other party" (keripy #1095). Issuee compromise is localized: "the ROI to the attacker for compromising the Issuee's keys is low," and prophylactic rotation already invalidates a thief's presentations. So Issuee-side detectability — a presentation/usage registry the Issuee controls and a `grant` must be anchored in — is an *optional* measure an Issuee elects and pays for, since "the Issuee must have its own Registrar." A reviewer who faults ACDC for not protecting Holders the way it protects Issuers has missed the asymmetry; a reviewer who assumes presentation registries are ambient has missed that they are opt-in, pre-normative, and unimplemented (bible 10 §1, §7). As of 2026-09-15 all three are sharper than that sentence implies. **Pre-normative** now rests on dated negatives on *both* ACDC lines — "presentation registry" has zero occurrences at `f0bd097de` and at `2362e48a1`, and `v1.1` leaves the `rd`-in-`a` ambiguity byte-identical to `main`. **Unimplemented** understates it: keripy does not merely lack support but now *enforces a rule a presentation registry violates by construction* — `vetBindings` requires an ACDC's `i` to equal the registry incepter's (@`b8f60166b`). And **the work is intended**, now on the written record rather than resting on an unquotable call: a SmithSamuelM comment on #1627 (2026-09-02) and PR #1674's body, both **status-and-intent only** under the fifth provenance class. A reader inferring *abandoned* from *unimplemented* is demonstrably wrong.

## Shibboleths & anti-patterns

Each row is an outsider framing whose shape encodes a rejected prior. The highest-leverage habit is to hear your own PKI/blockchain/OAuth reflex fire and catch it before it reaches the page.

|---|---|---|---|
| "Who is the trusted authority / who vouches for the identifier?" | Presumes an administrative root; KERI eliminates the role, it does not fill it. | The identifier is the root of trust; replay the KEL, no authority in the loop. | keri-primer §1.3; `cr-ad-trust.md` §4 |
| "The strength of the system is the rigor of the issuer's vetting." | Wrong locus of risk — CAs don't manage cert keys; holders' opaque key custody does. | Assurance lives in observable key management (pre-rotation, multisig, witnessing) declared in the public KEL. | x509-prob §Governance; keri-primer §2.4 |

| "Secure the pipe (TLS/VPN) and the data is safe." | Every pipe joint is a gap; SSL-visibility appliances MITM TLS by design; transport secures motion, not rest. | Move security with the data (message-level security / TSP); sign and where needed encrypt the payload itself. | ASAAU §3.6; GOC §8 |

## Evidence standard & self-check

**The evidence rule.** No finding may rest solely on a generic best-practice, PKI, IAM, consensus, or ZK analogy. An analogy is a hypothesis, not a finding. Every finding must:

1. **Cite ground truth** — a spec section (with line reference where available), a paper section, a `background.md` / security-analysis section, a keripy invariant or landmine, or a `file:line` in the reference code. "The prose says X" is not enough when a machine-behavior claim is at stake: verify against the code, because KERI's implementations contain real, documented gaps between doctrine and enforcement (DI2I and NOT recognized but unimplemented, failing closed with `ValidationError` @`b8f60166b`; the operator silently inferred when `o` is absent; DAG acyclicity unchecked; `WitnessReceiptor` waiting for all witnesses; pre-rotation going permissive on a digest-code mismatch; the credential `Verifier` possibly skipping `verifyAnchor`). **And verify spec claims against the spec** — a code comment asserting what a specification does is not evidence about the specification.

2. **State its objective function.** Name whether the finding is evaluated against survivability or invulnerability, and against which layer (KERI-core key-state continuity, ACDC disclosure, governance/EGF, or deployment). A finding that faults KERI-core for a property that lives in a higher layer (unlinkability, semantic agreement, issuer fitness) is aimed at the wrong target and must be re-aimed or cut. A finding that assumes an invulnerability objective must justify why prevention is required given KERI's threat model — the corpus notes this justification is almost never supplied.

3. **Distinguish the three buckets when raising a "weakness."** Every apparent KERI weakness in the formal literature resolves into one of: a deliberate non-goal, a proof-scope limitation, or a deployment/ecosystem-maturity gap (`background.md` §8.2 meta-pattern). Only the third bucket yields findings about KERI itself, and even then the finding is about the ecosystem (immature watcher tooling, the super-watcher's re-centralization, thin peer-reviewed literature, no eIDAS-equivalent standing), not the protocol. Say which bucket you are in.

**What still counts as a legitimate, surviving finding.** Do not swing to treating every KERI reframing as unassailable. A finding lands if it targets the real seams: whether a guard actually fails closed; whether the wire format is honored byte-for-byte across the four implementations; whether the layering actually composes (does the disclosure layer blind the labels it claims to? does the governance duty bind downstream? does the deployment actually rotate/segregate AIDs?); whether an assumption (A3, A5, A7, A8-A11) is silently granted; whether a "simplification" desyncs parsers; whether pre-rotation or SAID checks go permissive on new (Falcon/PQ) digest codes. These are in-terms findings and should be pressed hard.

**Two named residuals a reviewer is entitled to press, because the corpus concedes them.** Do not defend these away; the honest move is to state the concession and argue the scope.

- **The no-trusted-third-party maxim is knowingly relaxed for Issuee-side protection — in two distinct places, not one.** The first: Verifier-enforced protection against Issuee impersonation "violates the maxim that security not be dependent on a trusted third party, but for localized harm, the party most likely to be harmed is the Verifier (Validator), which provides incentives for them to protect themselves" (keripy #1095). It is a deliberate exception justified by blast radius and aligned incentives — not an oversight, and not something the maxim covers. **The second attaches to the very mechanism offered as the answer to the first**, and the corpus has not recorded it before: a presentation registry gives the Grantor "an Issuer-Verifier-protected mechanism to detect compromise of its signing keys" (keripy #1613) — it needs a **non-colluding third-party Issuer** *and* an **enforcing Verifier**, and #1613 states plainly that a self-issued origin ACDC forecloses the fraud-protection benefit. So the mechanism offered as Issuee *self*-protection is two-party-dependent at both ends. A reviewer quoting the maxim unconditionally is right about the tension and wrong to treat it as unacknowledged; a reviewer who grants the first exception and misses the second has conceded less than the design actually asks for.

- **Adversarial review by AI personas is a structured self-attack, not independent validation — and this file configures one.** A source inside this corpus retracted its own provenance claim in August 2026: `m-glance.md` v1.1 described "two independent adversarial expert reviews", and v1.2 corrects that to "AI models prompted to argue from a named lens, not by human domain experts", adding that "They are a structured way to attack one's own assumptions, not independent validation." `amp-diff.md` made the same move, from "internally adversarially reviewed" to "adversarially self-reviewed". Apply it on the same terms here. The `dg-c01..c06-claude.md` adjudications this doctrine leans on are model-authored by their own filenames, and so is any panel run against this file. That is not a reason to discount their findings; it is a reason never to describe a panel result as corroboration by an independent party, and to keep the thin-formal-literature residual standing rather than treating panel output as having relieved it.
- **Freshness is specified nowhere a standards process can reach.** KRAM governs replay protection for every non-key-event message and appears in no specification — the KERI spec's only trace is an imported glossary xref defining the weak (cache-less) variant, while keripy implements the strong one from a whitepaper in a personal repository (bible 09 §5). "It is not in the spec" is a legitimate, surviving finding here, and it is a governance/maturity finding rather than a protocol one — bucket three.

**Mandatory pre-ship self-check.** Before emitting any finding, ask: *Would a KERI core contributor recognize this as reasoning in KERI's own terms, or dismiss it as an outsider importing a PKI/IAM/blockchain/SD-JWT prior?* If the latter, cut it or reframe it. The tell that you have internalized the doctrine is not that you praise KERI — it is that for any given critique you can state whether it survives objective-function alignment, and cite why.
